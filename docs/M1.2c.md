# Evidence extraction and assembly

From the repository root, with the project installed in the development environment:

```text
python -m version_aware_retriever.acquisition verify
python -m version_aware_retriever.extraction build
python -m version_aware_retriever.extraction verify
```

All commands above are offline. `build` verifies all frozen inputs first, assembles
the complete result in memory, and replaces derived files only if bytes differ.
`verify` recomputes the artifacts and compares bytes without writing. A second
`build` preserves identical files, including modification times. A damaged input
blocks publication; no acquisition or repair is attempted. Each derived file is
replaced atomically, not the pair as a transaction. Run one writer; use `verify`
after an interrupted write to detect mismatched artifacts.

The explicit recipe is `data/pydantic/extraction/recipe.json`. It contains the
selection hash, registered source IDs, permitted line spans, assembly order,
contribution roles, actual heading-line references, include replacements, policy,
and proposed applicability annotations. Its allowed spans are the manual executable
transcription of the approved selection, including narrower helper/configuration
restrictions. They are a review boundary: changing that permission table requires
curation review. The utility cannot infer semantic restrictions from English.
Unit spans and basis locations are checked against that table and physical bounds.

Outputs are `data/pydantic/extraction/derived/evidence.json` and `inspection.md`.
The JSON wraps each serialized EvidenceUnit with a human inspection key; that key
is not an evidence ID. The report provides counts, full content quoted as data,
immutable original source links, source hashes, contribution offsets, explicit
formatting/include transformations, and proposed applicability bases for each unit.
Both derived files and the recipe should be committed after review. Frozen files,
selection, source identities, acquisition times, and licenses remain unchanged.
The inspection report's Git attributes preserve quoted upstream whitespace rather
than treating it as a formatting defect. No frozen-file attribute is changed.

There are 34 coherent units, below the approximate 38–40 target: 14 v1, 12 v2
non-migration, and 8 migration units (23.53%). Eleven are compound and 23 use a
single physical source. All 20 physical sources contribute. The extra-field
default and forbid examples remain together to preserve their shared explanation;
no filler or repetitive method-table rows were added to reach a quota. No approved
topic was dropped. Incidental APIs in approved examples are retained without
becoming new evaluation topics. The report records narrowed selections and limits.

Coordinate and assembly rules:

- Original spans are one-based, inclusive physical lines (`Lfirst-Llast`), split
  only at LF. UTF-8 decoding is strict; original newlines, whitespace, indentation,
  qualifiers, warnings, and tables are preserved.
- Assembled spans are zero-based, half-open Python string character offsets,
  never UTF-8 byte offsets. Applicability claim locators use `chars:start:end`.
- Every contribution maps an original span to its exact assembled extent. Its
  declared prefix/suffix may add only newline separators or Python Markdown
  fences under `explicit-lines-v1`. Those characters are formatting, not copied
  source bytes. No arbitrary technical-text insertion is supported.
- Include markers are omitted via explicit, checked primary-line to approved
  companion mappings. Their committed code is copied into fenced blocks. No
  generated files, recursive include processing, execution, or fabricated output
  is involved. Unmapped markers and companion attachments are rejected.
- The selected v2 model_validate code ends before its original closing fence;
  a declared suffix closes it without copying any model_validate_json text.
  The v1 parse_obj example excludes unrelated imports and sibling parsing code.
- Heading ancestry is resolved from explicit original heading lines as metadata;
  headings outside the selected body are never injected into content. For document
  introductions without headings, the original repository path is the root label.

Applicability uses only the two selected exact endpoints or UNKNOWN. Unqualified
endpoint documentation statements are proposed for that exact snapshot under the
documented recipe policy. Explicit V1/V2 transitions are bounded to these endpoints;
they do not assert coverage of all minor/patch releases or future releases. Mixed
passages (required fields, configuration, subclass serialization) retain separate
scoped endpoint and transition assertions. Source-qualified bases identify original
source lines; claim locators identify actual copied text in assembled content.
Neither capture time nor authority alone establishes behavioral applicability.
Deprecated syntax is not automatically unsupported.

All 34 units and their annotations are pending human review. No human or independent
review is claimed. Currently none requires UNKNOWN for its scoped proposed claim;
incidental historical notes or APIs need not be covered by those assertions.
Assertions are not an exhaustive guarantee about every statement in a unit. Tests
establish structural fidelity and reproducibility, not behavioral truth or gold
relevance. No complete Benchmark is fabricated for validation.

The evidence ID is `evidence:` plus SHA-256 of canonical UTF-8 JSON (sorted keys,
compact separators, Unicode unescaped) covering the assembled record with a fixed
`pending` ID placeholder, policy, ordered part specifications, include mappings,
and contributing source hashes. The record includes source IDs, selected spans,
contribution offsets, content hash, heading ancestry, and applicability annotations.
Capture times, absolute local paths, recipe inspection keys, and unit-list positions
do not enter identity. Content hashes are SHA-256 of assembled text encoded as UTF-8.
No text deduplication removes independently versioned provenance.

Limits: original links and MkDocs directives are quoted text, not rendered or
resolved. The v1 nested-subclass behavior is retrospective evidence in v2 sources.
The recipe's section choices and applicability explanations still need human
review. Extraction does not create questions, judgments, retrieval, or metrics.
