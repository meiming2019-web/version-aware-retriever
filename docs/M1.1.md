# M1.1: Benchmark data contracts and validation

The public records live in `version_aware_retriever.contracts`. They use frozen,
keyword-only standard-library dataclasses, enums, and immutable tuples. There are
no runtime dependencies. Constructors raise `ContractError` for invalid records.
No serialization format, retrieval behavior, or evaluation metric is implemented.

`SourceManifestEntry` represents one retained physical source snapshot. Official
companion example files use `DocumentType.DOCUMENTATION_EXAMPLE`; they are not
automatically separate retrieval units or folded into a fabricated source record.

`EvidenceUnit.source_id` and `source_locator` designate its primary document and
passage. Existing single-source records need no changes: empty `contributions`
means all content derives from that primary passage under the source's recorded
transformation. Explicit `contributions` require an `assembly_policy` identifier
or description and exactly one `primary_explanation` matching those primary
fields. Other roles are `companion_example` and `supporting_explanation`.

Each `SourceContribution` names a registered source, an original `source_locator`,
and a half-open `[content_start, content_end)` span in assembled `content`.
Offsets count Python string characters, not bytes. Contributions must partition
the full content without gaps, overlaps, or out-of-bounds spans. Formatting such
as an inserted newline belongs to an adjacent contribution under the assembly
policy; this mapping does not claim byte-for-byte copying. Distinct spans from
the same source are allowed. All contributing sources must share the evidence's
ecosystem. Source spans remain opaque locators; their existence and faithful
mapping require producer review, not a source parser in this module.

`ApplicabilityAssertion.content_locator` locates the claim in assembled evidence.
Its `basis_locator` locates justification in an original frozen source, qualified
by `basis_source_id`. With explicit contributions, this source ID is required and
must name a contributing source. The basis can reference contextual text outside
the contributed span in that same file. For legacy single-source evidence only,
an omitted basis source resolves to the primary source. Neither locator string
is parsed or assumed to use the other coordinate system. Gold judgment
`supporting_locators` refer to assembled evidence, whose contributions provide
the route back to original files; they do not implicitly name companion files.

`VersionSelector` supports exact versions, ranges, release lines, and unknown
applicability under a named scheme. Range bounds require explicit inclusivity;
open bounds require a basis. Ordering, membership, and release-line interpretation
are not inferred. Benchmark v0 queries require exact requested versions and exact
source versions for migrations. Lookups omit source versions, as specified.

`GoldJudgment` keeps topical relevance, version applicability, roles, and review
status independent. `is_valid_positive` requires direct relevance, valid
applicability, and reviewed/adjudicated status. Reviewed unknown applicability is
retained but earns no positive credit. A draft record can exist during curation.

`Benchmark` represents a complete reviewed revision: it rejects drafts, duplicate
identifiers or judgment pairs, broken references, incomplete judgment matrices,
and answerability inconsistent with valid positives. It checks source/evidence
ecosystem consistency and prevents cross-ecosystem positives. Human review must
still establish whether labels and answerability are factually justified.

`RankedRun.validate_against(benchmark)` checks the revision, exactly one result
per query, and known evidence IDs. `RankedResult.evidence_ids` is ordered accepted
evidence, with no duplicates; an empty tuple represents rejection of all evidence.
Poor retrieval results remain structurally valid runs. Validation does not reject
wrong-version returns or nonempty results on unanswerable queries.

Identifiers are opaque, nonblank, and whitespace-free. Producers must preserve
IDs for identical records and issue new IDs when their identity-bearing inputs
change. M1.1 cannot verify that historical guarantee from a single revision.
Contributing snapshot identities, selected source spans, content mappings, and
assembly policy are identity-bearing inputs even when visible content is unchanged.
Producers must account for them when issuing evidence IDs; the content hash alone
is not an evidence identity. No historical comparison or ID generator is provided.
Content hashes use `sha256:<64 lowercase hex digits>`; validation checks encoding,
not retained source bytes or content integrity. Snapshot immutability and source
locator resolution are also producer responsibilities at this boundary.

Optional technical identifiers and curator notes are available. Other optional
metadata from the specification (parent/related units, code-language annotations,
run scores) is deferred. Required provenance and contract fields are retained.

All fixtures in `tests/test_contracts.py` describe a fictional project and are
test-only. They are not part of the real benchmark. Tests use targeted type-checker
ignores only when deliberately supplying malformed runtime types.

With the project and declared dev extras installed, run:

```text
python -m pytest
python -m ruff check .
python -m ruff format --check src tests
python -m mypy
```
