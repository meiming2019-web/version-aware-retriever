## 如何理解标签 / Interpretation

- relevance **0**：与所问事实无关；**1**：有用背景，但不能直接建立所问事实；**2**：直接回应所问事实，版本是否适用另判。
- applicability **valid**：对该问题及指定角色有来源支持；**invalid**：有明确版本行为冲突；**unknown**：尚未建立问题相关的适用性，不等于错误。
- hard_negative 只提议用于 relevance 2 + invalid。文档版本不同、未出现答案、被弃用，都不能单独证明无效。
- source_behavior / target_behavior 分别可支持迁移的一端；transition 可同时建立变化。部分支持不等于整个问题已回答。
- 全部 review_status 为 draft；外层 human_review_status 为 pending。候选正例按 **relevance=2 且 applicability=valid** 显式统计，不能用会排除草稿的 is_valid_positive。此处不是评分。
- supporting_locators 是 assembled content 的半开字符区间，不是原文件行号。既有 contributions 映射回冻结源。无关项记录所检查的完整单元以便追溯，不伪造“证明不存在答案”的引文；background 在这些 0 分项仅满足现有必填角色，不表示有用背景。

端点政策：未限定版本的冻结文档行为只提议用于相应精确端点；明确 V1/V2 历史映射到 1.10.13/2.5.3，不推广到全部版本。稳定的 Python assert 规则结合两端一致文本讨论。S1 = `8822578619bf8d0bb754b1cf7a2a905b50240d01`，S2 = `9f58e785a5f1f2c34437f6e9b6adcd5b969e0df4`；以下路径在 `data/pydantic/frozen/sources/<commit>/` 下，行号含两端。

## q:a7c2 — 旧版本 TypeError 的出口

In Pydantic 1.10.13, if my @validator raises TypeError, does the caller receive TypeError or ValidationError?

- **v1-errors** (`evidence:d7267def0efc3affe89aebfe80b279bd6910209fc2db679c5c98f16571254127`): 2 / valid / requested_behavior。S1 `docs/usage/models.md` L177–179 lists “`ValueError`, `TypeError` or `AssertionError`” and “caught and used to populate `ValidationError`”。直接支持旧端点的包装规则。
- **migration-typeerror** (`evidence:4bd23223de4ab66136b4944b2145e5c28ddbbc025f58c337cac6bf182c323bc5`): 2 / valid / requested_behavior。S2 `docs/migration.md` L317–320: “Previously ... that error would be wrapped into a `ValidationError`”。v2 快照中明确的历史陈述可支持 v1，而不是把新规则倒套过去。
- **v2-validator-errors** (`evidence:a9c73c27473d19d0472e7ebb2f5a313950f5cc6ce9c5b3100f9aff1a5ece31ff`): 2 / invalid / hard_negative proposal。S2 `docs/concepts/validators.md` L472: “including `TypeError`” and “not wrapped in a `ValidationError`”。同一事实的相反端点规则，冲突由迁移说明证实；不是因为整篇每句话都错。

背景四项：v1-validators、v1-pre-item 为 1/valid，分别说明可抛出的异常和旧回调例子，但没有单独建立 TypeError 到达调用方的完整规则；v2-field-validators、migration-validator 为 1/unknown，相关回调/API 背景不能证明旧端点异常行为。

人工关注：v1-validators “should ... raise ... TypeError” 是否足够直接，还是保持背景；不要从推荐抛出直接推断完整传播机制。旧版本 answerable 提议保留。

## q:39fa — 错误签名调用的迁移变化

After upgrading from Pydantic 1.10.13 to 2.5.3, calling a function with the wrong signature inside my field validator raises TypeError directly instead of wrapping it in ValidationError. What changed?

直接候选三项：**migration-typeerror 2/valid** 同时带 transition/source_behavior/target_behavior；**v1-errors 2/valid** 仅 source_behavior；**v2-validator-errors 2/valid** 仅 target_behavior。完整 ID 同上，JSON 为每对独立保留。

决定性引文：S2 `docs/migration.md` L319–323 把 “calling a function with the wrong signature” 与旧 ValidationError 联系起来，并说明 “when a `TypeError` is raised in a validator, it is no longer converted into a `ValidationError`”。因此两端异常文本分别是有效的半边支持，不能把 v1-errors 当负例。

背景四项均 1/valid（仅限所述角色）：v1-validators、v1-pre-item 为 source/background；v2-field-validators 为 target/background；migration-validator 为 transition/background。最后一项讨论的是校验函数可接受的参数，不是校验函数内部错误调用其他函数的签名问题，两者不能混淆。

人工关注：是否同意一端事实也可记 relevance 2，但只有迁移单元或两端组合建立完整变化。answerable 提议保留；不推广到所有编程错误。
